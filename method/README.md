# LeanHardware method

Method source code is organized here into exactly two stage directories. Benchmarks and the CPU case study are separate directories at the repository root.

```text
method/
├── stage1/                         LeanSpec
│   ├── leanspec/                   formalization → diagnosis → clarification → revision
│   │   └── lean/
│   │       ├── LeanSpec/           partial relational specifications and diagnosis queries
│   │       └── SpecIR/             executable specification types / semantics
│   └── common/                     shared agent backend, confinement, provenance, paths
└── stage2/                         LeanRTL
    ├── v2lean/                     RTL-to-Lean parser / importers
    ├── leanrtl/                    agentic implementation, theorem proving, correction
    ├── framework/                  LeanRTL circuit semantics / compiler / refinement
    ├── refinement/                 fixed-target theorem contracts, replay, axiom audit
    ├── assets/                     proof library, prompts, authoring resources
    ├── audit/                      proof / interface / asset audits
    ├── profiles/                   workflow configuration
    └── example/                    small buildable framework examples
```

[Stage 1](stage1/README.md) produces clarified, frozen specifications. [Stage 2](stage2/README.md) proves that the Lean model of the actual RTL satisfies the specification. Both use the shared runtime support in `stage1/common/`; Stage 1 does not depend on Stage 2's circuit semantics.

The former `specir` is neither a third stage nor another name for the former `leanspec` package. The `LeanSpec` namespace provides the `admits` relation and diagnosis; the `SpecIR` namespace provides executable specification types such as `Val`, `Machine`, and `Design` for fixed-target refinement. Both now belong to Stage 1 / LeanSpec. Existing Lean namespaces are retained to preserve declarations and theorem meanings; there is no separate root-level `specir/` directory.

The Python module names `leanspec`, `leanrtl`, and `v2lean` remain available after `source env.sh` at the repository root. The former `specir.agent_backend` is now `common.agent_backend`. The project has one Lake configuration at the root.

The package integrity tool is also stored here: run `python3 method/check_package.py` from the repository root. Specification diagnosis documentation is in `stage1/docs/`; there are no separate root-level `scripts/` or `docs/` directories.

[MIGRATION.json](MIGRATION.json) records package sources and hashes; [VALIDATION.md](VALIDATION.md) records historical validation scope. Test-run `data/` is excluded from the source package and can be regenerated by the run entry points.
