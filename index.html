01 / Overview

Making AI-generated hardware trustworthy

Language models can generate RTL from natural-language specifications. Reliable hardware development also requires an explicit interpretation of the intended behavior and evidence that the implementation satisfies it.

CHALLENGE 01

Ambiguous requirements

Natural-language descriptions may permit several distinct behaviors. A plausible RTL implementation can still disagree with what the designer intended.

CHALLENGE 02

Functional correctness

Passing a finite set of simulations does not establish correctness for all relevant states or execution lengths.

OUR APPROACH

Executable intent + proof

LeanHardware clarifies requirements using discriminating traces, then uses Lean to prove that generated RTL refines the decided executable model.

Motivation

Two questions across hardware development

What behavior should the design implement? LeanHardware formalizes candidate interpretations and asks the designer targeted questions when the interpretations disagree.

Does the generated implementation satisfy that behavior? LeanHardware translates RTL into a Lean model and establishes a refinement relation through formal proof.

Interactive workflow

02 / Case Study

A RISC-V CPU: from one instruction to an end-to-end proof

Case study at a glance

LeanHardware verifies a concrete, five-stage RISC-V CPU by relating its cycle-by-cycle RTL execution to a transaction-level ISA model. The source-bound case covers a defined 38-instruction RV32 subset, including arithmetic, loads, and stores; this is not a claim of full RISC-V ISA compliance. The verification connects the imported RTL circuit, pipeline invariants, native RAM, and instruction retirement to architectural state.

What is proved. Following a specified reset, the actual RTL circuit's architectural projection agrees with its transaction-level reference for arbitrary finite lists of modeled cycles and inputs, under the stated relation and assumptions. A separate accepted-program result uses a final-drain assumption to equate the final state with the accepted instruction sequence.

1. One concrete instruction: ADD x3, x1, x2

Start with x1 = 7 and x2 = 9. ISA-level execution of ADD x3, x1, x2 must set x3 = 16 with 32-bit wraparound addition and advance the PC by four. It must also preserve other architectural registers, leave x0 unchanged, and preserve memory. Stalls and forwarding may change the timing, but not the visible result.

ISA.ADD(a, b) = (a + b) mod 2³² ADD x3, x1, x2: x3 ← 16 PC ← PC + 4 all other architectural registers unchanged

In the source-backed reference model, an instruction is a function over architectural state; no pipeline stage appears in this definition.

def isaStep (s : Arch) (i : Instr) : Arch := applyEffect s (effectFor s i) def isaRun : Arch → List Instr → Arch | s, [] => s | s, i::xs => isaRun (isaStep s i) xs

2. Find the corresponding computation in actual RTL

The deterministic HDL-to-LeanRTL translation imports word-level circuit nodes. In this CPU, w613 is an actual 32-bit addition node; w694 is the ALU mux output. Proving arithmetic correctness must therefore connect the selected ALU output—not merely a standalone mathematical adder—to the ISA operation.

{ name := "w613", width := 32, expr := (.add (.var "w577" 32) (.var "w574" 32)) } @[irreducible] noncomputable def V_w613 (b : Env) : BitVec 32 := ((V_w577 b) + (V_w574 b))

4. Cross the five-stage pipeline

ISA execution advances by an instruction, while RTL execution advances by a clock cycle. An instruction passes through IF, ID, EX, MEM, and WB; intermediate cycles can be architectural stuttering steps. Pipeline relations track valid packets, instruction identity, source and destination values, PC, results, and faults. Stalls preserve the relevant packet and control-state invariants; retirement applies the abstract instruction effect.

5. Compose local lemmas into an unbounded trace proof

The proof establishes a relation between the imported physical circuit state (including registers and memory) and a cycle-level reference. A single-cycle refinement is lifted to arbitrary finite execution lengths by induction, using reset initialization and invariant preservation.

theorem circuit_run_related (s : NativeMemory.State) (q : Raw.State) (xs : List (Raw.Pins × Env)) (h : Related (physical s.regs) (NativeRAM.ramView s.arrays) q) (hv : Raw.Valid q) : Related (physical (circuitRun s xs).regs) (NativeRAM.ramView (circuitRun s xs).arrays) (Raw.run q (xs.map Prod.fst)) := by induction xs generalizing s q with | nil => exact h | cons x xs ih => exact ih (rtlStep s x.1 x.2) (Raw.cycle q x.1) (circuit_cycle_refinement s x.1 x.2 q h hv) (Raw.valid_cycle q x.1 hv)

Finally, rtl_to_transaction_isa projects the circuit execution to architectural state and equates it to the transaction-level reference. The following theorem is reproduced from the previous detailed case.

theorem rtl_to_transaction_isa (s : NativeMemory.State) (seed : CaseCPU.Bridge.RF) (o : Env) (xs : List (Raw.Pins × Env)) : architecture (circuitRun (rtlStep s {reset := true,seed := seed} o) xs) = rtlReference (rtlStep s {reset := true,seed := seed} o) (initial (CaseCPU.Bridge.readRF seed) (NativeRAM.ramView s.arrays)) xs := by have hb := boot_related s seed o have ha := related_architecture _ _ hb rw [Raw.project_initial] at ha change architecture _ = initial _ _ at ha rw [←ha] apply rtl_port_isa_refinement _ _ xs hb (Raw.valid_initial _ _) rw [Raw.project_initial] exact initial_inv _ _
Interpretation. This is a proof over all finite execution lengths in its formal input domain, not a bounded simulation. It does not establish unconditional instruction completion under permanent stalls. The final architectural-state claim for accepted programs has additional no-reset and drain conditions.

6. Proof scope and specification decisions

The underlying reference contract specifies 38 supported RV32 instructions, RAM semantics, precise memory faults, reset behavior, stage ordering, and allowed stalls. For example, byte order is fixed as little-endian, RAM contents are preserved across reset while unretired stores are canceled, and LH sign-extends while LHU zero-extends.

Covered in the stated modelOutside the claim / qualifications
Defined 38-instruction RV32 subset; registers, PC, RAM, fault behaviorNo claim of complete RISC-V ISA compliance
Synchronous reset and arbitrary initial RAMNo branch/jump, CSR, cache, instruction RAM, MMIO or privilege behavior
Stalls and delays within the modeled safety tracesPermanent stalls do not imply unconditional progress
Architectural refinement at the specified observation boundaryDiagnostic counters are not included in the architectural projection

The trust boundary includes the stated Lean theorem and dependencies, Lean's checker and declared axioms, and the HDL-to-LeanRTL import and validation path. The specifications and environment constraints define exactly what the theorem means.
